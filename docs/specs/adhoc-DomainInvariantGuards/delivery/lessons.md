# adhoc-DomainInvariantGuards — Lessons

## Developer Lessons

- **Dot-anchored blast-radius greps miss object-initializer assignments.** The plan's grounding for Step 1 searched for `.Stage =` (member-access assignment) and concluded ArticleHub's read model was the only external write site. A bare `Stage = ArticleStage.Created` inside another class's object initializer (`Submission.Domain/Behaviors/Journal.cs:15`, inside `Journal.CreateArticle`) doesn't match that pattern but is exactly as build-breaking once the setter tightens — `private set` is scoped to the declaring class, not the namespace, so a same-namespace sibling class writing via initializer syntax fails to compile just like a cross-service caller would. When grounding an accessibility-tightening step, search both `\.{Prop}\s*=` (external member access) and `\b{Prop}\s*=\s*{EnumOrType}\.` (bare initializer-style assignment) — the second pattern is the one that hides in plain sight because it *looks* domain-internal (same file family, same namespace) without actually being a member of the type being tightened.
- **A skill's "already exists" precondition needs per-aggregate verification, not per-service.** Step 4 assumed the `add-state-machine` skill's Phase 1-3 were done for Asset because they were done for Article in the same service (Production). They weren't done symmetrically: `IArticleStateMachine`/`ArticleStateMachineFactory` live in `Production.Domain.StateMachines` (correct, per skill), but `AssetStateMachineFactory` was declared directly in `Production.Application.StateMachines` with no Domain-layer interface at all. Two state machines in the same service, only one wired per the skill's mandated shape. Worth a plan-time check: "does this aggregate's factory type live in Domain, like the sibling aggregate's does?" before marking a skill phase as already satisfied.
- **Threading a new required guard-dependency through an optional-action call path: make the dependency optional too, paired with the same null-check that already exempts that path.** `Asset.CreateAndAddFile`'s `action` parameter was already optional (`= null`) to support the materialization call site, which takes a guard-free direct-assignment branch. Adding the guard's `AssetStateMachineFactory` as a *required* parameter would have forced a dummy value at the materialization call site (or broken it outright); making it `AssetStateMachineFactory? = null` and only dereferencing it inside the existing `if (action is not null)` branch kept the exempt path's call site (2 args, unchanged) working with zero edits, while the guarded path (4 args) got the real factory. Look for the existing optionality signal before deciding a new parameter must be required.
- **A relocated guard whose data and algorithm are byte-for-byte unchanged doesn't need its own re-verification pass.** Step 4.4 asked to confirm the seed transition table covers the endpoint-exercised transitions. Since the guard's `CanFire` call and the seed data were untouched by this pass — only the *call site* moved (endpoint → domain) — the pre-existing endpoint guard already proved the coverage in production; re-deriving it from scratch would have duplicated work the plan's own Decision #3 anticipated might be unnecessary. When a plan step says "verify X still holds after a relocation," check first whether the relocation changed X's inputs at all before doing a full independent re-derivation.
- **A null-forgiving `!` on a threaded-through optional parameter is a self-flag, not just a compiler-silencer.** The reviewer caught what lesson #7 above didn't: making `stateMachineFactory` optional to preserve the exempt call site's signature also meant `SetState(AssetState.Uploaded, action, stateMachineFactory!)` was asserting non-null with no runtime backing — a caller passing `action` without `stateMachineFactory` (violates the *intended* coupling, but the compiler can't see that intent) hits a bare NRE instead of the domain's own `DomainException` idiom. Any time a fix reaches for `!` to satisfy the compiler on a value whose null-ness is coupled to a *different* parameter rather than genuinely guaranteed non-null by that point in the method, add the explicit coupling guard in the same edit — don't wait for review to catch it. `Blocks.Core.Guard` doesn't have an "either both or neither" helper and its existing helpers all throw non-`DomainException` types, so the fix here matched the file's own plain `if (...) throw new DomainException(...)` idiom rather than reaching for the shared Guard class.

## Architect Lessons

- **Type-move blast radius = grep the type *name*, not the guarded call sites.** Step 4 counted the guard's *call sites* (the `SetState` / `CheckAndThrowStateTransition` paths) and reported "the 5 endpoint call sites," but relocating the `AssetStateMachineFactory` *delegate type* from Application to Domain touches every file that names the type — 10 API files with `using Production.Application.StateMachines`, not 5. This is exactly the create-implementation-plan rule the plan skipped ("When enumerating files affected by a type move, grep for the type name — not import statements / not just the obvious call sites"). For any step that moves or relocates a type, the file list and the acceptance grep must both come from a `grep -rn {TypeName}` sweep, and — as here — a sibling reference file (`DependencyInjection.cs`) may already import the destination namespace and need *no* change, which only a name-grep reveals.
- **"No new types" in an accessibility-tightening pass collides with any in-scope goal that moves a guard into the domain.** prod-5 ("Asset transition guard belongs in the domain") is structurally infeasible without a Domain seam type (`IAssetStateMachine`), because Clean Architecture forbids Domain→Application references — so the plan's blanket "Domain Model Changes: no new types" contradicted its own ratified scope row. When a debt row requires a guard to move into a layer that can't currently see the guard's type, the seam type is mandatory; scope wording must carve it out up front ("no new domain *model* types; state-machine seam types are the sanctioned exception") rather than forcing a Phase-1 escalation. Check each in-scope "move X into the domain" row against the target layer's existing project references at plan time.
- **Ground accessibility-tightening steps with a non-dot-anchored grep.** (Reinforces the developer's Q1 lesson from the architect side.) Step 1's grounding used `.Stage =` and missed the bare `Stage = ArticleStage.Created` object-initializer assignment in a *sibling* class (`Journal.CreateArticle`), which `private set` breaks identically. A setter-tightening step's blast-radius grep must run both `\.{Prop}\s*=` and `\b{Prop}\s*=` — the second catches initializer-style writes from other classes in the same namespace that only *look* domain-internal.
- **The exemplar the pass converges on also dictates the *shape* of the compile-gap fix, not just the accessibility.** Q1's clean fix wasn't a new setter-seam but the same-class static factory both correct siblings already use (Review `Article.FromSubmission`, Production `Article.FromReview`) — so a "make siblings match the exemplar" pass should resolve incidental compile gaps by adopting the exemplar's construction idiom, keeping CLAUDE.md's "no inventing patterns" intact, rather than bolting on a bespoke seam.
- **Mechanism-based acceptance made the done-check fully deterministic — zero judgment calls.** Every load-bearing claim in the revised plan had a grep-or-build acceptance line (`using Production.Application.StateMachines` → 0, `delegate.*AssetStateMachineFactory` in Application → 0, `Stage = ArticleStage` in Submission → 1-in-factory, `TryDeleteAsync` in a catch, the Step-7 public-setter sweeps). At done-check I re-ran each and confirmed pass/fail by count, not by reading-and-judging code. The one place a false-positive *could* have crept in (the `File File { get; set; }` sweep matching `IFormFile File` and the `AssetCurrentFileLink` link row) was already pre-named DO-NOT-TOUCH in the plan's Scope, so the extra hits resolved in one line instead of an investigation. Takeaway: for a type-move/accessibility refactor, spend the plan-time budget on grep-shaped acceptance + an explicit DO-NOT-TOUCH carve-out for homonyms — it converts the entire done-check from read-and-judge into grep-and-confirm.

## Reviewer Lessons

- **A task's focus-area label can misname the actual location — verify the referent before reviewing it.** The Step-2 dispatch named "the nullable factory-param choice in Article.Create" as a focus area, but Submission's `Article.Create` (the Q1 factory) takes no factory parameter at all — Decision #4 explicitly rejected threading a state-machine factory through creation. The only nullable-factory-parameter design choice in the whole diff is on `Asset.CreateAndAddFile` (Production), a different type's different method. Grepped for the literal claim first, found it didn't exist where named, then located the actual pattern it almost certainly meant (same shape — a nullable `*Factory` parameter added by this pass) before writing a finding against it. A reviewer that reviews the label instead of verifying the referent risks either reporting a false "not found" or silently reviewing the wrong code. Worth a beat of grep-first verification whenever a dispatch message names a specific symbol as a focus area.
- **A relocated guard's coverage claim ("byte-for-byte unchanged") is worth an independent primary-source check, not just corroboration of implementation.md's prose.** Reading `AssetStateTransition.json`/`AssetStateTransitionCondition.json` directly (rather than trusting the developer's Step 4.4 summary) both confirmed the claim and surfaced a related pre-existing, out-of-scope risk (`CanFire`'s `_triggers[actionType]` dictionary indexer would throw `KeyNotFoundException`, not fail gracefully, for an action type absent from the seed table entirely) — worth checking whether that risk is reachable from any current call site before either filing it as a finding or dismissing it. Here it wasn't reachable (`Download` never reaches `CanFire`), so it stayed out of Findings, but the check needed the seed data read, not just the grep-count acceptance criteria.
